# Работа с GitHub: issue → PR → merge

Протокол обязателен для людей и агентов. Короткие правила — в `AGENTS.md`, шаблоны — в
`.github/`, тесты — в `docs/TESTING.md`, ревью кода — в `docs/REVIEW.md`.

## 1. Принципы

1. **Сначала issue, потом код.** Любая находка становится задачей в тот же момент. Исключение —
   аварийный hotfix (раздел 12), после которого issue заводится задним числом.
2. **Один PR — одна issue.** Не смешивать правку лендинга, движка и документации в одном PR.
3. **Доказательство важнее описания.** Тест, JSON-диф, скриншот или страница отчёта. Слова
   «проверил, работает» доказательством не считаются.
4. **Детерминизм.** В рантайме нет моделей, сети и внешних API (`docs/BRIEF.md:24`). Проверка,
   которую нельзя повторить, не становится проверкой.
5. **Данные не публикуем.** Ни текстов ТНПА, ни документации заказчиков, ни персональных данных.
   Для примеров — `samples/demo-project` и синтетика.
6. **Вкус судит владелец.** Агент и CI проверяют факты; визуальную приёмку делает только владелец.

## 2. Роли

| Роль | Кто | Что решает |
|---|---|---|
| Владелец | `dettram` | приоритет, визуальная приёмка, merge, релиз, спорные трактовки норм |
| Автор | человек или агент | issue, ветка, тесты, скриншоты, PR, ответ на замечания |
| Ревьюер кода | агент или владелец | `docs/REVIEW.md`, тесты, риск, отсутствие регрессий |
| Норм-ревьюер | владелец или профильный эксперт | шифры, пункты, статусы, замена, юридическая гигиена |
| Security-ревьюер | владелец | upload, пути, ZIP, subprocess, сеть, секреты, зависимости |
| CI | машина | циклы импортов, сборка, smoke, тесты, наличие скриншотов |

Один человек может совмещать роли, но проверки от этого не отменяются. Автор не оценивает
собственную визуальную работу как «принято».

## 3. Issue

### 3.1 Типы и шаблоны

| Тип | Шаблон | Метка | Когда |
|---|---|---|---|
| Ошибка | `bug.yml` | `bug` | проверка пропускает дефект, отчёт падает, разметка ломает файл |
| Задача | `feature.yml` | `enhancement` | новая проверка, формат отчёта, интерфейс, документация |
| Пробел в нормах | `norm-gap.yml` | `norms` | нормы нет в фонде, шифр не опознан, пункт не находится |
| Документация | `feature.yml`, область «документация» | `documentation` | расхождение docs и кода, неясная инструкция |

Пустые issue запрещены (`blank_issues_enabled: false`). Security-находка не описывается
публично: сначала владелец, потом issue с меткой `security` без эксплойта и данных.

### 3.2 Метки

| Группа | Метки | Кто ставит |
|---|---|---|
| Тип | `bug`, `enhancement`, `norms`, `documentation` | автор или шаблон |
| Область | `report`, `ui`, `landing`, `accessibility`, `corpus` | автор |
| Состояние | `status: triage`, `status: ready`, `status: in-progress`, `status: review`, `status: blocked` | триаж и исполнитель |
| Флаги | `security`, `needs-info`, `no-visual`, `duplicate`, `wontfix` | триаж, владелец |

У issue ровно одна метка типа, одна метка состояния и хотя бы одна метка области. `status:`
ставит не автор, а тот, кто ведёт issue.

### 3.3 Как завести

1. Поискать дубль: открытые и закрытые issue по шифру, файлу, тексту ошибки.
2. Выбрать шаблон; не писать свободным текстом.
3. Заголовок — что не так, без «улучшить» и «оптимизировать».
4. Тело: что происходит, как повторить, что считаем правильным, где код (`файл:строка`).
5. Приложить доказательство: команда, вывод, JSON, скриншот, страница нормы.
6. Указать область и severity (3.6), данные проверить на безопасность.
7. Назначить себя, если берёшь issue; чужое не перехватывать.
8. Поставить `status: triage` — дальше триаж.

### 3.4 Триаж: как проверяем issue

Проверка занимает до одного рабочего дня. Чек-лист:

- [ ] **Воспроизводится** на `samples/demo-project` или минимальной синтетике; команда в issue.
- [ ] **Не дубль**; если дубль — закрыть со ссылкой, а не удалять.
- [ ] **В границах продукта**: не расчёты, не DWG/RVT, не полный текст норм, не юридическая
      экспертиза (`README.md`, «Ограничения»).
- [ ] **Данные безопасны**: нет документации заказчика, полных текстов ТНПА, персональных данных.
- [ ] **Критерии приёмки измеримы**: что должно стать иначе, на каком файле, чем проверим.
- [ ] **План доказательства**: тест, скриншот, JSON-диф или страница отчёта.
- [ ] **Severity и область** проставлены.

Итог триажа — одно из четырёх:

| Итог | Действие |
|---|---|
| `status: ready` | criteria есть, evidence понятен, issue можно брать |
| `needs-info` | вернуть автору конкретные вопросы; 30 дней без ответа — закрыть с причиной |
| `duplicate` | закрыть со ссылкой на основную issue |
| `wontfix` | закрыть с причиной; не удалять |

### 3.5 Definition of Ready

Issue готова, когда:

1. Есть воспроизведение и фактическое/ожидаемое поведение.
2. Есть критерии приёмки — проверяемые, не «стало лучше».
3. Понятно, чем подтвердим: тест, скриншот, JSON, DOCX/PDF.
4. Указаны границы: что входит и что **не** входит.
5. Определён риск: данные, безопасность, совместимость, производительность.
6. Есть оценка: S (до дня), M (2–3 дня), L (неделя); L дробится на части.
7. Для норм — шифр, пункт и страница, а не «где-то написано».

Issue без критериев приёмки в работу не берётся.

### 3.6 Severity

| Уровень | Что | Реакция |
|---|---|---|
| S1 | потеря данных, ложный «всё чисто», утечка, падение отчёта | в тот же день, hotfix |
| S2 | неверное замечание, пропущенная проверка, сломанная выгрузка | 1–3 дня |
| S3 | текст, вёрстка, неудобство, неясная ошибка | в плановую волну |
| S4 | идея, «хотелось бы» | бэклог, без обещаний |

### 3.7 Состояния

| Состояние | Метка | Кто двигает | Условие перехода |
|---|---|---|---|
| Новое | `status: triage` | автор | issue заведена по шаблону |
| Готова | `status: ready` | триаж | DoR выполнен |
| В работе | `status: in-progress` | исполнитель | есть ветка, WIP ≤ 2 |
| На ревью | `status: review` | исполнитель | PR открыт, проверки зелёные |
| Заблокирована | `status: blocked` | любой | причина в комментарии, владелец знает |
| Закрыта | — | владелец | DoD выполнен, evidence в PR |

### 3.8 Закрытие

Закрываем только когда:

- критерии приёмки выполнены и проверены;
- есть тест (для правила/бага) или скриншот (для видимого);
- обновлены docs, если поведение изменилось;
- в PR есть итоговый комментарий: что сделано, чем проверено, что осталось.

«Исправлено» без проверки — не закрытие. Если находка оказалась неверной, закрываем с причиной,
а не удаляем.

| Тип | Definition of Done |
|---|---|
| bug | падающий до фикса тест; «до/после»; старые тесты зелёные |
| feature | тест правила; артефакт (скриншот/JSON/DOCX); docs; детерминизм |
| norms | шифр, пункт, страница, источник статуса; тест на фикстуре; без полного текста |
| docs | рабочие ссылки; нет противоречий; `файл:строка` актуальны |
| UI | 1440 и 390; пусто/ошибка/загрузка; клавиатура; скриншоты в PR |
| corpus | manifest и SHA-256; лицензия; нет данных заказчика |

### 3.9 Планирование

- Горизонт — волны из `docs/PLAN.md`; milestone = волна или релиз.
- У issue один milestone; без milestone — бэклог.
- Активная волна одна; WIP ≤ 2.
- S1/S2 идут в текущую волну, S3/S4 — в бэклог без обещаний.
- Раз в неделю 10 минут: снять `blocked`, закрыть зависшее, пересмотреть бэклог.

## 4. Ветки и коммиты

- Ветка: `fix|feat|test|docs|chore/<N>-<slug>`, например `fix/42-pair-window`.
- Коммит: `type(scope): короткая суть (#N)`, например `fix(engine): окно пары 80 знаков (#42)`.
- Один коммит — одна мысль; тесты можно отдельным коммитом в той же ветке.
- Перед PR — rebase на свежий `main`; merge-коммиты не тянем.
- В `main` не пушим напрямую; force-push в `main` запрещён.

## 5. Pull request

1. Открывать draft PR сразу после первого коммита — видно статус и проверки.
2. Заголовок: `type(scope): суть (#N)`.
3. Тело — по `.github/PULL_REQUEST_TEMPLATE.md`: issue, что изменилось, как проверить,
   скриншоты, данные, риск, чек-лист.
4. `Closes #N` — issue закроется после merge.
5. Размер: до 400 изменённых строк без учёта фикстур и скриншотов. Больше — дробить или
   объяснять в PR, почему нельзя.
6. Автор сначала читает свой diff целиком; потом просит ревью.
7. Merge — squash, сообщение из заголовка PR, ветку удалить.

## 6. Доказательства: скриншоты и не только

### 6.1 Когда скриншот обязателен

| Что менялось | Что приложить |
|---|---|
| `app/ui/**`, лендинг | 1440 и 390 px; для `fix/` — «до/после»; изменённые состояния (пусто, ошибка, загрузка) |
| отчёт DOCX/PDF | страницу с изменённым блоком (DOCX → PDF → PNG), для `fix/` — до/после |
| разметка Word | документ с комментарием и подсветкой, видно место и текст |
| правило движка | JSON-диф или вывод CLI на `samples/demo-project`; скриншот — если это видно в UI |
| документация | не нужен; нужны рабочие ссылки и отсутствие противоречий |
| норма | карточка/страница источника и короткая цитата; полный текст не прикладывать |

Если изменение видно на экране, скриншот обязателен. Если не видно — обязателен другой
воспроизводимый артефакт.

### 6.2 Требования к кадру

- Реальный продукт, не макет и не рисунок «как будет».
- Видно место изменения; для UI — адрес `127.0.0.1:8765/app` или `/`.
- Данные — только демо; пути, имена и адреса заказчика замазаны или заменены.
- PNG/WebP, ширина 1440 или 390; полная страница или аккуратный кроп, не скриншот всего экрана
  с рабочим столом.
- Обе темы — только если в интерфейсе есть переключатель. Сейчас его нет: одна светлая тема.

### 6.3 Куда класть и как вставлять

```
docs/pr-assets/<N>/00-before.png
docs/pr-assets/<N>/01-after-1440.png
docs/pr-assets/<N>/02-after-390.png
```

`<N>` — номер issue, `NN` — порядок. Репозиторий **приватный**: `raw.githubusercontent.com`
в issue и PR отдаёт 404, картинка не отображается. Загружаем файл вложением GitHub и вставляем
полученный URL:

```powershell
powershell -ExecutionPolicy Bypass -File tools/attach-image.ps1 -Path docs/pr-assets/42/00-before.png
# → https://github.com/user-attachments/assets/…
```

```markdown
![до](https://github.com/user-attachments/assets/…)
![после](https://github.com/user-attachments/assets/…)
```

Файлы всё равно лежат в `docs/pr-assets/<N>/` — вложение только для показа. Ссылка на `blob`
картинку в тексте не показывает.

### 6.4 Приёмка доказательства

Владелец проверяет: кадр показывает именно изменение, а не соседний экран; состояние
воспроизводится; «до» и «после» отличаются тем, о чём issue. Кадр без изменённого элемента
доказательством не считается.

CI дополнительно проверяет: если в PR менялся `app/ui/**`, должен появиться добавленный или
изменённый файл-картинка в `docs/pr-assets/`. Метка `no-visual` отключает проверку — только с
объяснением в PR, почему изменение невидимо.

## 7. Тесты

Полная матрица — `docs/TESTING.md`. Коротко:

- баг: сначала падающий тест, потом исправление;
- новое правило: тест на синтетической фикстуре и на `samples/demo-project`;
- изменённый поток UI: скриншот + e2e, если поток менялся;
- отчёт/разметка: проверка структуры DOCX и хотя бы одна страница PDF/PNG;
- тесты не зависят от `~/.stroy-audit`, корпуса норм и установленного Word — иначе `skip` с
  причиной;
- новое правило — с тестом; покрытие ядра не ниже 75%, общий процент по репозиторию не KPI;
- flaky-тест не «перезапускаем», а чиним или удаляем с причиной.

Без теста правило не считается проверкой. Без доказательства баг не считается исправленным.

## 8. Гейты и CI

| Проверка | Команда | Блокирует |
|---|---|---|
| циклы импортов | `uv run python tools/check-imports.py` | да |
| синтаксис | `uv run python -m compileall -q app scripts tools samples` | да |
| smoke движка | `uv run --with python-docx --with pypdf python app/engine.py --path samples/demo-project --out demo.json` | да |
| тесты | `uv run --with-requirements requirements-dev.txt python -m pytest -q` | да |
| скриншоты для UI | job `evidence` | да, после включения в branch protection |
| лендинг | `gate.mjs`, `copy-lint`, `consistency` | вручную, владелец |
| security | чек-лист раздела 9 | при триггере |
| нормы | шифр, пункт, статус, источник | для `norms` |

Локально перед PR:

```powershell
uv run python tools/check-imports.py
uv run python -m compileall -q app scripts tools samples
uv run --with python-docx --with pypdf python app/engine.py --path samples/demo-project --out demo.json
```

Правила CI: Ubuntu, Python 3.13, без корпуса и Word, токен только на чтение, отмена устаревших
прогонов, таймаут 10 минут. Секретов в workflow нет. Actions закреплять по версии, при
возможности — по SHA.

Branch protection для `main`:

- прямой push запрещён, обязателен PR;
- обязательны `smoke` и `evidence` (после включения);
- linear history, force-push запрещён;
- approvals: 0 пока владелец один; 1, когда появится второй человек;
- административный bypass — только для инцидента, с записью в issue.

## 9. Ревью

### 9.1 Автор перед запросом

- [ ] diff прочитан целиком, отладочного кода и `print` нет.
- [ ] тесты/скриншоты приложены, команды воспроизводимы.
- [ ] docs обновлены; `файл:строка` в issue и PR актуальны.
- [ ] нет данных заказчика, текстов норм, секретов, внешних вызовов.
- [ ] commit message и заголовок PR по формату.

### 9.2 Ревьюер

- [ ] Логика: правило детерминированное, границы и ложные срабатывания понятны.
- [ ] Тесты: покрывают баг/правило, не проходят «сами по себе», нет зависимости от корпуса.
- [ ] Ошибки: файл не прочитан, скан, пустая страница — видны, а не проглочены.
- [ ] Интерфейс: состояния пусто/загрузка/ошибка, клавиатура, контраст, 390 px.
- [ ] Производительность: 600 файлов / 80 страниц не превращаются в вечность.
- [ ] Безопасность: пути, ZIP, upload, subprocess, сеть, секреты.
- [ ] Документация: поведение и ограничения описаны честно.

Вердикт — коротко: **«Принято»** или **«Блокеры:»** со списком `файл:строка → что сделать`.
«Улучшить» без конкретного действия блокером не считается. Вкус — только владелец.

Security-триггеры: upload, пути и ZIP, subprocess/COM, сеть, секреты, auth, новые зависимости.
Норм-триггеры: любой шифр, пункт, статус, замена, цитата.

## 10. Merge и релиз

1. Все обязательные проверки зелёные, блокеры закрыты, владелец сказал «ок».
2. Squash merge, заголовок `type(scope): суть (#N)`, ветку удалить.
3. После merge: `git switch main`, `git pull`, smoke на демо, issue закрыта.
4. Релиз — тег `v0.x.y`; notes по группам: breaking, features, fixes, docs, tests.
5. Если менялись правила норм — обновить (или создать) `docs/BENCHMARK.md` и записать
   precision/recall.
6. Релиза без зелёного CI не бывает.

## 11. Метрики

| Метрика | Как считаем | Цель |
|---|---|---|
| Lead time | issue ready → merge | S2 ≤ 3 дня, S3 ≤ 2 недели |
| Размер PR | изменённые строки | ≤ 400 |
| Escaped defects | баги, найденные после merge | снижать, каждый — с тестом |
| Покрытие | pytest-cov по ядру (engine, common, norm_check, clause, history) | ≥ 75% |
| Точность правил | precision/recall на бенчмарке | публиковать в `docs/BENCHMARK.md` |
| Скриншоты | PR с UI-изменениями и кадром | 100% |
| WIP | issue в работе | ≤ 2 |

Раз в месяц — 15 минут: что зависло, какие проверки пропустили, какие тесты flaky. Количество
issue метрикой не считаем.

## 12. Исключения

- **Hotfix S1**: ветка от `main`, минимальная правка, тест, PR, ускоренное ревью. Если совсем
  горит — merge с записью в issue, но тест и разбор после обязательны.
- **Security/утечка**: остановить работу, убрать артефакт, сообщить владельцу, при необходимости
  сменить ключи, записать в issue без чувствительных деталей.
- **Блокировка**: `status: blocked` + причина + что нужно от владельца.
- **Отказ**: `wontfix` с причиной; issue не удаляем.
- **Зависшая issue**: 30 дней `needs-info` — закрыть с причиной.

## 13. Настройки репозитория

- Issues включены, пустые запрещены, шаблоны и метки на месте.
- Wiki и Discussions выключены: знания живут в `docs/`, вопросы — в issue.
- Projects — по желанию; источник истины — метки, а не доска.
- Actions: `GITHUB_TOKEN` только на чтение, секретов нет, PR из форков без секретов.
- `main`: PR, обязательные `smoke` и `evidence`, linear history, force-push запрещён.
- Релизы — теги `v0.x.y`; notes по группам.
- Security — приватный канал владельцу, публичная issue без деталей.
